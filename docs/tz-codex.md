# Помойка — Telegram-only MVP. ТЗ для Codex

Ты выступаешь в роли Senior AI Architect. Спроектируй и построй автоматический
конвейер, который парсит проверенные мировые СМИ, отбирает подлинные абсурдные
новости, переписывает их на русском языке и автоматически публикует в Telegram-
канал. Никакого сайта, никакого фронтенда. Реализация — максимально просто,
быстро, с нулевыми расходами на инфраструктуру.

## 1. Контекст и механика

- **Суть:** конвейер полностью автоматический. Человек в цикле нужен только для
  первичного списка источников и периодической правки промпта редактора.
- **Пайплайн:** RSS-парсинг проверенных СМИ → двухэтапная LLM-фильтрация
  (скоринг абсурдности 1–10 + safety-фильтр) → перевод и рерайт на русском →
  сохранение в БД → автопостинг в Telegram-канал по расписанию.
- **Формат продукта:** только Telegram-канал. Никакого сайта, никакой статики,
  никакого хостинга фронтенда.
- **Язык вывода:** только русский. Источники могут быть на любом языке — перевод
  и рерайт на русский делает LLM на этапе рерайта.
- **Источники — жёсткое ограничение:** только редакции с профессиональным
  редакционным и фактчекинговым процессом (традиционные СМИ, включая жёлтую
  прессу и региональные издания). Категорически запрещены: Reddit, Telegram-
  каналы, форумы, соцсети, сатирические издания (The Onion, Le Gorafi, Panorama
  и подобные — держим их домены в чёрном списке в коде, не полагаясь только на
  LLM). Цель — только подлинные, реально произошедшие новости.
- Монетизация в этом ТЗ не реализуется — только конвейер и публикация.

## 2. Технический стек (неизменяемый)

- **База данных:** Supabase (PostgreSQL), бесплатный tier.
- **Скрипт парсера/фильтра/постинга:** Node.js.
- **Расписание:** GitHub Actions cron, интервал 30–60 минут.
- **LLM API:** модель задаётся параметром в `.env` (например, дешёвый tier вроде
  gpt-5.4-nano или аналог) — код не должен жёстко зависеть от конкретной модели.
- **Публикация:** Telegram Bot API, собственный бот с правами администратора в
  канале.
- Фронтенда, статического хостинга, платежей — нет.

## 3. Требования к базе данных (Supabase)

Таблица `sources`:
- `id` (uuid, primary key)
- `name` (text) — название издания
- `rss_url` (text, unique)
- `region` (text) — страна/регион
- `active` (boolean, default true)

Таблица `news`:
- `id` (uuid, primary key)
- `source_id` (uuid, foreign key → sources.id)
- `original_url` (text, unique) — защита от дублей
- `title_original` (text) — заголовок на языке источника
- `title_rewritten` (text) — переписанный заголовок на русском
- `content_summary` (text) — выжимка на русском, 1–2 абзаца
- `absurdity_score` (float)
- `safety_flag` (boolean) — true для криминала/политики/трагедий/насилия
- `source_published_at` (timestamp) — дата публикации у источника
- `fetched_at` (timestamp) — время, когда наш парсер её увидел
- `posted_to_telegram` (boolean, default false)
- `telegram_message_id` (text, nullable)
- `posted_at` (timestamp, nullable) — момент реальной публикации в канал (не
  путать с `fetched_at`); нужен для группировки постов по календарным суткам
  в дайджесте (раздел 10)

Записи с `safety_flag = true` сохраняются в БД (для последующей калибровки
промпта), но никогда не публикуются и не учитываются при отборе.

## 4. Список источников (первая загрузка в `sources`)

Список ниже — стартовый набор. Перед первым запуском Codex обязан вручную
проверить, что RSS-адрес каждого издания актуален (адреса разделов меняются),
и вписать в БД проверенные значения, а не предполагаемые.

**Великобритания:** The Sun (раздел Weird/News), Daily Star, Metro UK, Mirror
(Weird News).
**США:** New York Post (Weird But True), UPI Odd News.
**Германия:** Bild (Vermischtes/Kurioses).
**Франция (жанр «faits divers» — курьёзные локальные происшествия, отдельная
институциональная рубрика французской прессы):** Ouest-France, La Dépêche du
Midi, Nice-Matin.
**Испания (рубрика «sucesos»):** региональные издания — уточнить конкретные
названия и RSS на этапе загрузки.
**Азия (проверенные, профессионально редактируемые издания на английском
языке, публикующие курьёзные/офбит-новости региона):**
- SoraNews24 (Япония, пул поп-культурных и бытовых курьёзов, профессиональная
  редакция)
- Coconuts (панрегиональная цифровая редакция по Юго-Восточной и Восточной
  Азии — Сингапур, Бангкок, Джакарта, Манила, Гонконг; известна разделом
  offbeat/crime-курьёзов)
- The Times of India (проверить актуальный RSS соответствующего раздела)
**Мировые агентства как мост для регионов без прямого RSS-покрытия (Латинская
Америка и часть Азии):** Reuters, AP, AFP — использовать их ленты как
дополнительный источник уже проверенных агентством историй, а не парсить
национальные редакции напрямую там, где нет уверенности в фактчекинге.

## 5. Требования к парсеру

- Скрипт читает активные строки `sources`, тянет RSS, создаёт черновую запись
  в `news` со статусами по умолчанию (без LLM-обработки).
- Дедупликация на уровне `original_url` (unique constraint) — обязательна.
- Дополнительная дедупликация: перед вставкой сверять нормализованный
  заголовок с последними ~200 записями в БД (одна и та же новость расходится
  по десяткам изданий с разными URL).
- Отдельно фиксировать `source_published_at` из RSS и `fetched_at` — не
  путать эти поля.

## 6. Требования к LLM-фильтру

- Двухэтапная обработка:
  1. Дешёвый скоринг по заголовку + первым ~300 символам — только оценка
     абсурдности и safety_flag.
  2. Полный рерайт (перевод на русский, хлёсткий заголовок, выжимка 1–2
     абзаца) — только для записей, прошедших порог по итогам этапа 1.
- Промпт редактора хранится в отдельном файле `prompts/editor.md`, не зашит в
  код. Файл состоит из двух блоков, оба заполняет владелец проекта (не Codex):
  1. **Якоря оценки** — 5–10 реальных новостей с оценкой абсурдности от 1 до
     10, которую поставил бы владелец, плюс 1–2 примера-ловушки (звучит
     дико, но на деле криминал/трагедия → `safety_flag = true`, а не высокий
     балл). Это не жёсткая рубрика начисления баллов, а именно якорные
     примеры, на которые ориентируется модель.
  2. **Примеры авторского стиля** — 15–30 пар «сырая новость → как владелец
     переписал бы это сам» (можно взять из его собственного Telegram-канала).
     Модель переносит стиль по этим примерам (few-shot), отдельного
     дообучения модели не требуется.
  Оба блока — живой, регулярно редактируемый материал, не разовая настройка.
  Код должен просто читать файл целиком и не должен ничего в нём парсить
  структурно (никаких жёстких полей) — это текст для LLM, а не конфиг.
- Строгий JSON-ответ от LLM:
  `{ "is_absurd": boolean, "score": number, "safety_flag": boolean,
  "rewritten_title_ru": string, "summary_ru": string }`.
- Жёсткий запрет в промпте: не добавлять факты, которых нет в источнике.
  Итоговый пост обязан содержать ссылку на оригинал.
- Проверка домена источника на сатирический чёрный список — выполняется в
  коде до вызова LLM, не полагаемся на то, что модель сама распознает сатиру.
- `safety_flag = true` (обычный криминал, политика, реальные трагедии,
  насилие) — запись сохраняется, но не публикуется.

## 7. Требования к публикации в Telegram

- Публикуются только записи с `absurdity_score >= 7`, `safety_flag = false`,
  `posted_to_telegram = false`.
- Формат поста: переписанный заголовок → короткая выжимка → название
  источника и ссылка на оригинал.
- После успешной публикации — `posted_to_telegram = true`,
  `telegram_message_id` заполняется.
- Публикация — через Telegram Bot API, токен бота и id канала — в
  переменных окружения GitHub Actions (secrets), не в коде.

## 8. Отказоустойчивость по оплате LLM

- Ошибка вызова LLM API (нет баланса, невалидный ключ) не должна ронять весь
  скрипт и не должна помечать запись как обработанную — запись остаётся в
  статусе "не обработано" и подхватывается следующим запуском крона.
- После 3 подряд неудачных запусков LLM-этапа бот отправляет владельцу личное
  сообщение в Telegram с текстом об ошибке оплаты/ключа. Использовать тот же
  Bot API, отдельная инфраструктура не нужна.

## 9. Изображение к посту

- Никакой генерации через ИИ (DALL-E-класс и подобные) — не используем: это
  ощутимо дороже текстового этапа и непредсказуемо по модерации именно на
  самом абсурдном контенте.
- Вместо этого — рендер простой брендированной карточки на сервере: фон +
  `title_rewritten` крупным текстом + название источника внизу. Библиотека
  для рендера HTML/CSS → PNG (например, `@vercel/og` или `node-canvas`),
  без обращения к внешним платным API.
- Публикация поста — через `sendPhoto` с этой карточкой и текстом (заголовок,
  выжимка, источник, ссылка) в `caption`, а не через `sendMessage`.

## 10. Дайджест дня

Как в обычном новостном медиа — раз в сутки отдельный пост-подборка, поверх
уже опубликованных за день записей.

- **Отбор:** топ-5–7 записей по `absurdity_score` среди тех, у кого
  `posted_at` попадает в последние календарные сутки. Это не новый контент —
  все эти записи уже выходили отдельными постами в течение дня, дайджест их
  просто пересобирает.
- **Формат:** один пост-список. На каждую позицию — переписанный заголовок
  (`title_rewritten`) одной строкой + ссылка на исходный пост в самом канале
  (`https://t.me/<channel_username>/<telegram_message_id>`), не на источник —
  ссылка на источник уже есть в оригинальном посте, дублировать её тут не
  нужно.
- **Без LLM-вызова.** Дайджест — это чистое форматирование уже готовых
  записей из БД, никакого нового обращения к нейросети не требуется, стоимость
  не растёт.
- **Заголовок поста** должен явно сообщать, что это подборка дня (например
  «Итоги дня»), чтобы подписчики не путали повтор заголовков с новым
  контентом.
- **Картинка** — тем же механизмом рендера, что и обычные посты (раздел 9),
  с фиксированным текстом вроде «Итоги дня» вместо заголовка конкретной
  новости.
- **Расписание** — отдельный, суточный GitHub Actions cron, не совпадающий с
  основным (30–60 минут). Конкретное время (UTC) и `channel_username`
  задаются в `.env`, значения уточняются с владельцем проекта, не
  придумываются самим Codex.

## 11. Что нужно выдать прямо сейчас

Проанализируй эти вводные и выдай **Master Plan** из 4 технических шагов для
последующей пошаговой реализации. Для каждого шага укажи: какие файлы
создаются, какие контракты (форматы данных, сигнатуры функций) должны
соблюдаться, и какие тесты нужно провести до перехода к следующему шагу.

Перед шагом 1 есть отдельный **Шаг 0**, который выполняет не Codex, а владелец
проекта: заполнить `prompts/editor.md` первой версией обоих блоков (якоря
оценки и примеры стиля из раздела 6). Код шага 3 не может быть протестирован
без этого файла, но сам файл — не код и не входит в зону ответственности
Codex.

- Шаг 1: схема Supabase (`sources`, `news`) + загрузка стартовых источников из
  раздела 4 (с проверкой актуальности RSS-адресов).
- Шаг 2: парсер RSS → сырые записи в `news`, без LLM. Тест: прогон по всем
  источникам без падений, дубли по `original_url` не проходят.
- Шаг 3: двухэтапный LLM-фильтр и рерайт, промпт в `prompts/editor.md`,
  модель в `.env`. Тест: ручной прогон 200 записей, визуальная проверка
  соответствия оценок ожиданиям.
- Шаг 4: Telegram-бот, публикация по расписанию через GitHub Actions. Тест:
  три автозапуска подряд без вмешательства человека, посты приходят в канал
  в правильном формате.
- Шаг 5: дайджест дня (раздел 10), отдельный суточный workflow. Тест: ручной
  запуск workflow, дайджест приходит в канал со ссылками на реальные посты
  этого дня, повторного вызова LLM в логах быть не должно.

**Запрещено выполнять более одного шага за один запрос.** Переход к
следующему шагу — только после того, как тесты предыдущего шага пройдены.
